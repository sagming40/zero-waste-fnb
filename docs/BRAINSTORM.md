## 1. 왜 다시 설계하나

2026-11-07에 레포를 다시 열어 본 상태:

- 커밋 5개가 모두 2026-07-12 하루에 몰려 있다. origin/main과 같고, 작업 트리는 깨끗하다.
- 구현된 것: Express 5 + pg로 만든 `GET /api/health` · `GET /api/inventory` · `POST /api/sales`(트랜잭션을 일부러 안 건 "before" 버전), `schema.sql`(테이블 7개), Python 더미 시드.
- 없는 것: 프런트 · 예측 파이프라인 · 인증(`userId = 1` 고정) · 입력 검증 · 테스트.
- 버릴 코드가 200줄 남짓이라 **기존 코드를 고치는 것보다 스택을 새로 고르는 쪽이 싸다**고 판단했다.

옛 코드는 지우기 전에 태그 `v0-express`로 남긴다. 아직 만들지 않았다.

**목표 (집 PC, 2026-11-07)**: v0는 개발 경험이 거의 없을 때 짠 설계라 허술할 가능성이 높다. 스택만 바꾸는 게 아니라 **프런트 · 백엔드 · DB · 서버 · 배포 · 운영 · 코드 구현 전부를 처음부터 탄탄하고 정교하게** 다시 설계한다. 취업 일정에 쫓기지 않는 자기계발 프로젝트라 시간이 걸려도 완성도를 우선한다.

**가져갈 것**: README의 문제 정의 · 핵심 기능, `schema.sql`의 테이블 설계(Flyway 마이그레이션으로 옮김), 더미 데이터 규칙(정기 휴무 · 예외 휴무 · 요일 가중치 · 말차라떼 콜드스타트, `random.seed(42)`), 딥 태스크 5개(`BE_트러블슈팅.md`).
**버릴 것**: Express 코드 전부, Python 파이프라인 계획(가중 이동 평균은 pandas 없이 SQL이나 Java 몇 줄이면 된다), CRA · React 계획.

### 2.2.1 DB 접근 (확정 2026-11-07, 12절 데이터 모델을 보고)

| 층 | 선택 | 메모 |
|---|---|---|
| DB 접근 | **Spring Data JPA + JdbcClient** | CRUD(계정 · 매장 · 메뉴 · 식자재 · 레시피 · 입고)는 JPA. SQL이 강한 쿼리(로트 `FOR UPDATE` 차감 · 마감 통째 교체 · 윈도 함수 WMA · 백테스트 · 손실 원화 · 탄소 리포트 · 외부 데이터 UPSERT, 8~10개)는 JdbcClient로 SQL 직접. SQL 쿼리는 기능 패키지마다 SQL 전용 클래스 하나(`StockQueries` 등)에 모으고, 그 클래스마다 Testcontainers 테스트를 반드시 붙인다(문자열 SQL의 오타는 실행해야 드러난다) |
| 패키지 구조 | **기능별 + Spring Modulith 검사 테스트** (확정 2026-11-07) | `store/` · `menu/` · `closing/`(마감) · `stock/` · `forecast/` · `external/` · `common/`, 각 폴더 안에 controller · service · repository. Modulith는 "기능끼리 규칙대로만 부르는지" 검사 테스트만 쓴다. 모듈 이벤트는 쓰지 않는다 — 마감 저장 → 재고 차감은 한 트랜잭션이어야 하는데 이벤트는 커밋 뒤에 돈다 |

- 뺀 것: **jOOQ**(타입 안전 SQL이지만 코드 생성 빌드가 M0를 무겁게 한다) · **QueryDSL**(국내 채용에서 흔하지만 JPQL 위라 윈도 함수 · `ON CONFLICT`를 못 한다, 원본 관리 중단) · **MyBatis / jOOQ 단독**(JPA 딥 태스크를 잃는다)
- 틀 여지: M4쯤 SQL 문자열이 괴로우면 그 쿼리들만 jOOQ로 옮겨 전후 비교 — 딥 태스크 후보

## 4. 딥 태스크

옛 `BE_트러블슈팅.md`의 5개에 PostgreSQL을 깊게 쓰는 후보 2개를 더했다. **6 · 7번은 넣을지 아직 안 정했다.**

| # | 주제 | 이 스택에서 |
|---|---|---|
| 1 | N+1 → JOIN · 인덱스 | JPA 지연 로딩에서 저절로 생긴다 → fetch join · `@EntityGraph` · 배치 사이즈 비교, `EXPLAIN ANALYZE`로 전후 ms를 잰다 |
| 2 | 트랜잭션 | 반쪽 저장을 테스트로 먼저 재현 → `@Transactional`. 함정도 소재다: checked 예외는 기본적으로 롤백되지 않고, 같은 클래스 안에서 호출하면 프록시를 타지 않는다 |
| 3 | 배치 멱등성 | 두 번 돌려 중복을 확인 → `ON CONFLICT DO UPDATE`(네이티브) |
| 4 | 엣지 케이스 | 휴무일과 판매 0을 구분하기, 신규 메뉴 콜드스타트 |
| 5 | 배포 | 환경변수 · 프록시 · DB 연결 · JVM 메모리 |
| 6 (**넣는다**, 2026-11-07 · 규칙은 12.4) | **행 수준 보안(RLS)** | 남의 매장 데이터를 막는 두 번째 벽. 앱의 `WHERE user_id`를 빼먹어도 DB가 막는다. JPA + 커넥션 풀에서 트랜잭션마다 현재 매장 ID를 DB에 넘기는 게 어렵다 — 그 어려움이 소재 |
| 7 (**넣는다**, 2026-11-07 · 12.5) | **윈도 함수로 예측 특징 · 백테스트** | SQL이 특징(WMA · 기준선 · 품절)을 뽑고 Java가 보정. 백테스트를 Java 반복 vs SQL 윈도 함수 한 번으로 돌려 시간 · 쿼리 횟수 비교 |

## 5. 사전 검증에서 찾은 설계 구멍

옛 설계를 끝까지 따라가 보다가 발견한 것. 실제로 겪은 오류는 아니다.

1. **휴무일과 입력 누락을 구분할 수 없다.** 판매 행이 없으면 쉰 날인지 안 적은 날인지 모른다. 딥 태스크 4의 전제가 깨진다.
   → `business_days`(날짜 · 영업/휴무)를 두고 마감 입력 때 함께 저장한다.
2. **재고가 변하는 흐름이 없다.** `current_stock`을 바꾸는 곳이 없어서, 발주 권장량("예측 − 재고")이 매일 같은 재고로 계산된다. → **열린 질문**:
   - A. 마감 입력 때 BOM으로 재고 자동 차감 + 입고 입력 화면 (추천: 계산이 실제로 돌아간다)
   - B. 마감 때 남은 재고를 직접 적기(실사). 입력은 늘지만 오차가 안 쌓인다
   - C. 재고는 수동으로만 고치기. 제일 단순하지만 발주 계산의 의미가 줄어든다
   - → 이 질문을 넓혀서 9절에서 다시 본다 (재고를 "원장"으로 두면 A + B를 같이 할 수 있다)
3. **단위가 안 맞을 수 있다.** `recipes_bom.unit`(g)과 `ingredients.unit`(kg)이 다르면 계산이 틀린다.
   → BOM 단위는 식자재의 기본 단위로 고정하고 `recipes_bom.unit`은 없앤다.
4. **같은 날을 두 번 입력할 수 있다.** 지금은 두 번 쌓인다.
   → (매장, 날짜, 메뉴)에 UNIQUE를 걸고, 다시 입력하면 그날 것을 한 트랜잭션 안에서 통째로 바꾼다.
5. **시간대**: 서버는 UTC라 "자정" 배치가 한국 시간 오전 9시에 돌 수 있다.
   → cron에 `Asia/Seoul`을 지정하고, 날짜는 모두 KST 기준으로 다룬다.
6. **탄소 환산 계수에 근거가 없다.** 음식물 쓰레기 1kg당 CO₂e를 얼마로 칠지, 출처와 함께 decisions에 남긴다.
7. **남의 매장 데이터**: 모든 조회를 세션의 매장 ID로 거르고, 남의 `menu_id`로 입력하면 거부되는지 테스트한다. (6번 딥 태스크 RLS와 이어진다)
8. **폐기가 무엇을 버렸는지 모른다.** `daily_waste`는 하루 총량(kg) 하나뿐이라 폐기분을 재고에서 뺄 수 없고, 재료별 탄소 계수 · 폐기 비용도 못 낸다. (집 PC, 2026-11-07) → 9절
9. **수량이 `REAL`(부동소수)이다.** 0.1 + 0.2 ≠ 0.3이 재고 합계에 쌓인다. → DB는 `NUMERIC`, Java는 `BigDecimal`. (집 PC, 2026-11-07)
10. **유통기한이 식자재마다 하나다.** 우유를 화요일 · 금요일에 들여오면 유통기한이 둘인데 한 칸에 못 담는다 → 9절 로트

## 9. 재고 · 폐기 확장 (논의 중)

> 집 PC에서 시작(2026-11-07). 취업 일정에 쫓기지 않는 자기계발 프로젝트라, 5절 2번(재고 흐름)을 "실제 매장에서 쓸 만한 재고 관리"까지 넓혀 본다.
> 아직 고른 것은 없다. 아래는 후보와 각각 무엇을 배우게 되는지다.

**뼈대 생각: 재고를 숫자 한 칸이 아니라 "원장"으로 둔다.**
`ingredients.current_stock`을 고쳐 쓰는 대신, 재고가 움직일 때마다 한 줄씩 쌓는다(통장 거래 내역처럼). 지금 재고 = 그 줄들의 합.
움직임 종류: 입고 · 판매 차감(BOM) · 폐기 · 실사 조정 · (생산 투입).
→ 5절 2번 A(자동 차감)와 B(실사)를 같이 할 수 있다: 평소엔 자동으로 빼고, 가끔 실사로 맞추면 그 차이가 "조정" 줄로 남는다.

| # | 확장 후보 | 무엇이 생기나 | 배우는 것 |
|---|---|---|---|
| E1 | **재고 원장** (위) | 언제 왜 재고가 바뀌었는지 전부 추적 | 불변 기록 설계, 집계 쿼리, 합계 스냅샷(성능), 트랜잭션 |
| E2 | **로트 · 유통기한** | 입고마다 로트(유통기한 포함). 차감은 유통기한 빠른 것부터(FEFO) | 할당 알고리즘, 동시 차감 시 락(낙관적 · 비관적) |
| E3 | **폐기 원인 · 식자재별 폐기** | 유통기한 만료 / 조리 실수 / 당일 판매 잔여(베이커리) / 손님 잔반. 재료별 탄소 · 원화 손실 | enum · 도메인 모델링, 원인별 분석 쿼리. "판매 잔여"는 과잉 생산 신호라 예측 개선에 쓴다 |
| E4 | **반제품 BOM (중첩 레시피)** | 크루아상 → 반죽 → 밀가루 · 버터. 반죽을 미리 만들어 둘 수 있다 | 재귀 CTE(`WITH RECURSIVE`), 순환 참조 막기 |
| E5 | **구매 단위 ↔ 사용 단위** | 우유는 1L 팩 12개 박스로 사고 ml로 쓴다. 발주는 박스 단위로 올림, 최소 주문량 | 값 객체(Value Object), `BigDecimal`, 단위 변환 |
| E6 | **공급처 · 발주서 → 입고 검수** | 발주(대기 → 보냄 → 일부 입고 → 완료), 리드타임만큼 미리 발주 권장 | 상태 기계, 리드타임을 넣은 발주 계산 |
| E7 | **실사 (재고 조사)** | 이론 재고 vs 실제 → 차이 리포트(로스율) | E1 조정 줄, 리포트 쿼리 |
| E8 | **원가 · 손실 원화** | 입고 단가 → 메뉴 원가율, 폐기 손실을 원으로 | 단가 평균(이동평균 · 선입선출), 사장님에게는 탄소보다 돈이 먼저 와닿는다 |
| E9 | **생산 계획 (베이커리)** | 내일 판매 예측 → 아침에 몇 개 구울지 → 재료 투입 | 예측 → 생산 → 재고가 이어지는 흐름 |

### 10.1 v0 개요에서 찾은 구멍

### 10.2 정한 것 (2026-11-07)

| 항목 | 결정 |
|---|---|
| 주 지표 | **돈과 탄소 두 축.** 매일 화면은 손실 원화 · 폐기율, 월간 · 누적 리포트는 재료별 탄소 감축량. 탄소는 프로젝트 정체성이라 빼지 않는다. 예측 오차(백테스트)는 내부 지표 → E8(원가)이 M 후보로 올라오고, 재료별 탄소 계수 출처를 decisions에 남긴다 |

### 11.3 조사 결과 (2026-11-07)

**매장 위치 (F02)**
- 1안 **도로명주소 API**(행정안전부, [business.juso.go.kr](https://business.juso.go.kr/addrlink/openApi/apiExprn.do)): 주소 검색 API + [주소별 좌표 검색 API](https://www.data.go.kr/catalog/15056663/openapi.json)가 따로 있다. 좌표 키는 승인이 1~2영업일 걸린다는 2차 자료가 있다
- 2안 [카카오 로컬 API](https://developers.kakao.com/docs/latest/ko/local/common): 주소 검색과 좌표(WGS84)를 한 번에. 무료 쿼터는 계정의 첫 앱에만, 2026-07-21에 쿼터 방식이 바뀌었다
- **확정 (2026-11-07): 1안** — 공공 데이터라 결과를 DB에 저장하는 데 걸림이 적다(국토부 지오코더는 저장 금지라 뺀다). 매장 등록은 매장당 한 번이라 호출 수는 문제가 아니다
- 확인할 것: juso 좌표의 좌표계 — UTM-K(GRS80)로 기억하는데 맞다면 위경도(WGS84)로 바꾸는 변환이 필요하다. 위경도 → 기상청 격자(nx, ny)는 기상청 활용가이드의 변환 공식을 Java로 옮긴다. ASOS 관측 지점은 지점 목록에서 가장 가까운 곳

**탄소 계수 (F20)** — 숫자가 두 종류다
- **생산 탄소** (버린 음식을 만드는 데 이미 든 탄소, 농장 → 매장): 대부분이 여기다. 출처 1안 **Poore & Nemecek (2018), Our World in Data 공개본** — 식품 약 40종의 kg당 CO₂e 전 세계 평균. 식자재의 "탄소 분류"(F05)를 이 40종에 연결한다(밀 · 우유 · 커피 · 달걀 · 치즈 · 소 · 돼지 · 닭 · 감자 · 토마토 · 채소 · 과일 …). 더 촘촘한 대안: Wolfram Food Carbon Footprint(500종+) · Foodsteps Open 100(영국)
- **처리 탄소** (버린 뒤 매립 · 퇴비화에서 나오는 메탄): 국내 연구값 기준 음식물 1톤당 메탄 매립 25.71kg · 퇴비화 4.00kg · 바이오가스화 1.00kg. 국내는 직매립 금지 · 사료화 · 퇴비화가 기본이라 생산 탄소보다 훨씬 작다
- **확정 (2026-11-07): 생산 탄소(Poore & Nemecek, OWID)를 주 숫자로, 처리 탄소는 작게 더하거나 빼고 이유를 적는다.** "감축량" = 폐기 감소량 × 계수. 메뉴 폐기(남은 빵)는 레시피로 재료를 펼쳐 계산한다
- 확인할 것: OWID · Poore 데이터의 라이선스와 출처 표기 방식, 국가 온실가스 인벤토리의 공식 처리 계수 → decisions에 남긴다

## 12. 데이터 모델 (초안, 2026-11-07)

> 추천안을 그대로 채택하고, 구현하면서 더 나은 방법이 보이면 튼다. 굳으면 `DATA_MODEL.md`로 옮기고, 컬럼은 Flyway 마이그레이션이 원본이 된다.

### 12.1 테이블 지도

| 묶음 | 테이블 | 하는 일 |
|---|---|---|
| 계정 · 매장 | `app_user` · `store` · `store_member`(점주 / 직원) · `store_invitation` | 한 사람이 여러 매장에 속할 수 있다. 매장은 위치(좌표 · 기상 격자 · 관측 지점 · 지역 코드)를 가진다 |
| 기준 정보 | `menu` · `ingredient` · `recipe_item` | 메뉴 = 고정 분류 + "당일 생산품" 표시. 식자재 = 기본 단위 + 탄소 분류 |
| 마감 | `business_day` · `daily_menu_sale` | 하루 = 영업 / 휴무. 메뉴 줄에 생산 · 판매 · 남은 수량 · 품절 여부 · 그날 가격 |
| 재고 | `stock_lot` · `stock_movement` · `waste_record` | 원장 = 추가만. 로트에 "남은 양"을 같이 두고 같은 트랜잭션에서 맞춘다 |
| 예측 | `forecast_run` · `forecast` · `production_reco` · `order_reco` · `backtest_result` | 실행 단위로 저장(모델 버전 · 외부 신호 유무) |
| 공용 | `holiday` · `weather_observation` · `weather_forecast` · `carbon_factor` · `external_fetch_log` | 매장과 무관. 외부 원본은 `jsonb`로 남긴다 |
| 세션 | Spring Session JDBC 테이블 | 재시작해도 로그인 유지, Valkey 불필요 |

### 12.2 기술 규칙

1. 모든 매장 데이터에 `store_id`를 직접 둔다(자식 테이블 포함)
2. 매장 데이터끼리는 `(store_id, id)` **복합 외래 키**로 참조한다 → 남의 매장 메뉴 · 재료를 DB가 거부한다(5절 7번)
3. 수량 `NUMERIC`, 돈 원 단위 `bigint`, 영업일 KST `DATE`, 시각 `timestamptz`
4. 원장은 추가만, 틀리면 반대 줄. 로트 "남은 양" = 원장 합계를 테스트로 지킨다
5. 마감 줄에 그날 판매가 · 로트에 입고 단가를 찍어 둔다(가격이 바뀌어도 지난 손실이 안 바뀐다)
6. 예측은 실행 단위로 저장한다
7. 세션은 PostgreSQL(Spring Session JDBC)
8. **마이그레이션을 고치는 규칙**: 첫 배포(M2 뒤) 전까지는 개발 DB를 지우고 `V1`을 고쳐도 된다. 첫 배포 뒤로는 새 번호 파일만 더한다

### 12.4 RLS (넣기로 함, 2026-11-07 · M2)

앱의 `WHERE store_id = ?`가 첫 번째 벽, RLS가 두 번째 벽이다. 사전 검증에서 찾은 함정과 규칙:

1. **현재 매장은 트랜잭션마다 넘긴다**: 트랜잭션 시작 때 `set_config('app.store_id', ?, true)`(= `SET LOCAL`). 커넥션 풀에서 커넥션이 재사용되므로 세션 단위로 걸면 남의 매장 값이 남는다. 정책은 `store_id = current_setting('app.store_id', true)::bigint`
2. **값이 없으면 0건** (실패해도 닫힌 쪽으로). 트랜잭션 밖 조회 · 설정을 빼먹은 코드는 아무것도 못 본다
3. **DB 역할을 나눈다**: Flyway가 쓰는 소유자 역할과 앱이 쓰는 역할을 따로 둔다. 테이블 소유자 · 슈퍼유저는 RLS를 건너뛰기 때문 — `FORCE ROW LEVEL SECURITY`도 건다
4. **테스트 함정**: Testcontainers 기본 계정은 슈퍼유저라 RLS가 안 걸린다 → 테스트도 앱 역할로 접속해야 한다. 안 그러면 "테스트는 통과, 운영에서 무방비"
5. **쓰기도 막는다**: 정책에 `WITH CHECK`를 붙여 남의 `store_id`로 INSERT · UPDATE를 거부한다(복합 외래 키와 이중)
6. **매장 밖 테이블은 RLS 없음**: `app_user`, 공용 데이터(`holiday` · 날씨 · `carbon_factor`). `store_member` · `store_invitation`은 로그인 · 매장 고르기 전에 읽어야 해서 따로 정한다(M2)
7. **배치는 매장마다 돈다**: 자정 예측은 매장 목록을 돌며 매장마다 트랜잭션 + `app.store_id`. RLS를 건너뛰는 배치 전용 역할은 만들지 않는다
8. **매장 바꾸기**: 한 사람이 여러 매장에 속하므로 "지금 매장"은 세션에 두고, 고를 때 `store_member`로 권한을 확인한다
9. 성능: 모든 매장 테이블의 인덱스는 `store_id`가 맨 앞

### 12.5 예측 계산을 SQL과 Java로 나누기 (딥 태스크 7, 확정 2026-11-07 · M4)

옛 안("WMA를 Java로 한 번, SQL로 한 번 짜서 비교")은 날씨 · 공휴일이 섞이면 SQL 쪽이 버티지 못해 비교 범위가 WMA로 쪼그라든다. 대신 **경계를 나눠서 둘 다 실제로 일하게** 한다.

- **SQL(윈도 함수) = 과거 데이터에서 특징 뽑기**: 메뉴 × 날짜마다 요일 가중 WMA, 기준선 2개(어제 `LAG(1)`, 지난주 같은 요일 `LAG(7)`), 최근 변동폭, 품절일 표시(품절 날은 WMA에서 빼거나 따로 표시). 휴무일은 `business_day`로 걸러낸다
- **Java = 그 위에 보정**: 날씨 · 공휴일 · 행사 배율, 콜드스타트(같은 분류 평균), 생산 · 발주 권장 계산. 둘 사이는 "특징 한 줄" 레코드 하나로 주고받는다
- **비교 거리는 백테스트에서 생긴다**: 180일 × 메뉴 13개의 "그날 기준 예측"을 다시 계산할 때 — Java 반복(날마다 쿼리 → N+1 모양) vs SQL 윈도 함수 한 번. 실행 시간 · 쿼리 횟수를 잰다(🧩1과 이어진다)
- (선택) 날씨 민감도: PostgreSQL 집계 함수 `regr_slope` · `corr`로 메뉴별 "기온 1도당 판매 변화"를 SQL로 추정해 Java 보정 배율의 근거로 쓴다
- 감수할 것: 계산이 두 언어에 나뉜다 → 경계 레코드를 고정하고 양쪽 테스트를 따로 둔다

### 12.3 운영 규칙 (사용자 결정)

| # | 질문 | 결정 |
|---|---|---|
| Q1 | 당일 생산품 마감 입력 | **만든 수량 · 남은 수량 · 품절 여부(+ 대략 시각)**. 판매 = 만든 − 남은. 품절 날은 판매량이 수요보다 작다(검열된 수요) → 예측에서 따로 다룬다 |
| Q2 | 남은 수량의 행방 | **폐기 / 할인 판매 / 직원식 / 기부**로 나눈다. 기본값은 폐기. 기부 · 직원식은 탄소 · 손실에서 폐기와 다르게 센다 |
| Q3 | 메뉴 분류 | **고정 분류**(음료 · 베이커리 · 샐러드 · 샌드위치 · 도시락) + 메뉴마다 "당일 생산품" 표시. 콜드스타트는 같은 분류 평균 |
| Q4 | 재료 차감 시점 | **마감 입력 때 한 번에**. 당일 생산품 = 만든 수량 × 레시피, 그 밖 = 판매량 × 레시피. 남은 빵 재료는 만들 때 이미 썼으니 다시 안 뺀다 |

### 13.1 그대로 가져오는 것

| 항목 | 방식 | 참고 |
|---|---|---|
| 배포 | CI가 이미지를 GHCR에 커밋 해시 태그로 올리고 서버는 받기만. `task deploy` | PlayLedger `deploy/` · SERVER 2절 |

### 13.2 이 프로젝트에서 새로 정한 것

1. **JVM 메모리** (🧩5의 핵심): Spring Boot는 JVM만 300~500MB. `MaxRAMPercentage` · 컨테이너 메모리 제한 · 스왑을 잡고 **실제 사용량을 재서** 서버 크기를 정한다
2. **배치 감시**: 헬스 응답에 "마지막 예측 성공이 몇 시간 전인지" · 외부 수집 상태를 넣고, 26시간 넘으면 uptime이 실패한다 — 앱은 살아 있는데 배치만 죽는 경우를 잡는다
3. **헬스 체크**: Actuator `/actuator/health`(DB · 디스크 · 마지막 배치). 바깥에는 health만 열고 다른 actuator는 닫는다
4. **DB 계정 둘**: Flyway = 테이블 소유자(`spring.flyway.user`), 앱 = 앱 역할(RLS 대상). 백업 · 복원도 역할 둘을 챙긴다
5. **로그**: Spring Boot 기본 JSON 로그, 요청마다 번호(추적 ID), Docker 로그 크기 제한. 로그 서버(ELK 등)는 쓰지 않는다
6. **시간**: 코드는 현재 시각을 직접 부르지 않고 `Clock`을 주입받는다 → 테스트에서 자정 · KST 날짜 경계를 만든다
7. **CI**: 백엔드(`./gradlew test` + Modulith 검사, Testcontainers는 GitHub 러너의 Docker로), 프런트(pnpm 린트 · 테스트 · 빌드), main이면 이미지 빌드

- Dependabot 의존성 알림: 첫 배포 때 켠다
