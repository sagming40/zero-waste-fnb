## 1. 왜 다시 설계하나

2026-11-07에 레포를 다시 열어 본 상태:

- 커밋 5개가 모두 2026-07-12 하루에 몰려 있다. origin/main과 같고, 작업 트리는 깨끗하다.
- 구현된 것: Express 5 + pg로 만든 `GET /api/health` · `GET /api/inventory` · `POST /api/sales`(트랜잭션을 일부러 안 건 "before" 버전), `schema.sql`(테이블 7개), Python 더미 시드.
- 없는 것: 프런트 · 예측 파이프라인 · 인증(`userId = 1` 고정) · 입력 검증 · 테스트.
- 버릴 코드가 200줄 남짓이라 **기존 코드를 고치는 것보다 스택을 새로 고르는 쪽이 싸다**고 판단했다.

옛 코드는 지우기 전에 태그 `v0-express`로 남긴다. 아직 만들지 않았다.

**목표 (집 PC, 2026-11-07)**: v0는 개발 경험이 거의 없을 때 짠 설계라 허술할 가능성이 높다. 스택만 바꾸는 게 아니라 **프런트 · 백엔드 · DB · 서버 · 배포 · 운영 · 코드 구현 전부를 처음부터 탄탄하고 정교하게** 다시 설계한다. 취업 일정에 쫓기지 않는 자기계발 프로젝트라 시간이 걸려도 완성도를 우선한다.

**가져갈 것**: README의 문제 정의 · 핵심 기능, `schema.sql`의 테이블 설계(Flyway 마이그레이션으로 옮김), 더미 데이터 규칙(정기 휴무 · 예외 휴무 · 요일 가중치 · 말차라떼 콜드스타트, `random.seed(42)`), 딥 태스크 5개(`BE_트러블슈팅.md`).
**버릴 것**: Express 코드 전부, Python 파이프라인 계획(가중 이동 평균은 pandas 없이 SQL이나 Java 몇 줄이면 된다), CRA · React 계획.

## 4. 딥 태스크

옛 `BE_트러블슈팅.md`의 5개에 PostgreSQL을 깊게 쓰는 후보 2개를 더했다. **6 · 7번은 넣을지 아직 안 정했다.**

| # | 주제 | 이 스택에서 |
|---|---|---|
| 1 | N+1 → JOIN · 인덱스 | JPA 지연 로딩에서 저절로 생긴다 → fetch join · `@EntityGraph` · 배치 사이즈 비교, `EXPLAIN ANALYZE`로 전후 ms를 잰다 |
| 2 | 트랜잭션 | 반쪽 저장을 테스트로 먼저 재현 → `@Transactional`. 함정도 소재다: checked 예외는 기본적으로 롤백되지 않고, 같은 클래스 안에서 호출하면 프록시를 타지 않는다 |
| 3 | 배치 멱등성 | 두 번 돌려 중복을 확인 → `ON CONFLICT DO UPDATE`(네이티브) |
| 4 | 엣지 케이스 | 휴무일과 판매 0을 구분하기, 신규 메뉴 콜드스타트 |
| 5 | 배포 | 환경변수 · 프록시 · DB 연결 · JVM 메모리 |
| 6 (후보) | **행 수준 보안(RLS)** | 남의 매장 데이터를 막는 두 번째 벽. 앱의 `WHERE user_id`를 빼먹어도 DB가 막는다. JPA + 커넥션 풀에서 트랜잭션마다 현재 매장 ID를 DB에 넘기는 게 어렵다 — 그 어려움이 소재 |
| 7 (후보) | **윈도 함수로 WMA** | 3번에 붙인다. 가중 이동 평균을 Java로 짠 버전과 SQL 윈도 함수 버전의 결과 · 속도 · 읽기 쉬움을 비교 |

## 5. 사전 검증에서 찾은 설계 구멍

옛 설계를 끝까지 따라가 보다가 발견한 것. 실제로 겪은 오류는 아니다.

1. **휴무일과 입력 누락을 구분할 수 없다.** 판매 행이 없으면 쉰 날인지 안 적은 날인지 모른다. 딥 태스크 4의 전제가 깨진다.
   → `business_days`(날짜 · 영업/휴무)를 두고 마감 입력 때 함께 저장한다.
2. **재고가 변하는 흐름이 없다.** `current_stock`을 바꾸는 곳이 없어서, 발주 권장량("예측 − 재고")이 매일 같은 재고로 계산된다. → **열린 질문**:
   - A. 마감 입력 때 BOM으로 재고 자동 차감 + 입고 입력 화면 (추천: 계산이 실제로 돌아간다)
   - B. 마감 때 남은 재고를 직접 적기(실사). 입력은 늘지만 오차가 안 쌓인다
   - C. 재고는 수동으로만 고치기. 제일 단순하지만 발주 계산의 의미가 줄어든다
   - → 이 질문을 넓혀서 9절에서 다시 본다 (재고를 "원장"으로 두면 A + B를 같이 할 수 있다)
3. **단위가 안 맞을 수 있다.** `recipes_bom.unit`(g)과 `ingredients.unit`(kg)이 다르면 계산이 틀린다.
   → BOM 단위는 식자재의 기본 단위로 고정하고 `recipes_bom.unit`은 없앤다.
4. **같은 날을 두 번 입력할 수 있다.** 지금은 두 번 쌓인다.
   → (매장, 날짜, 메뉴)에 UNIQUE를 걸고, 다시 입력하면 그날 것을 한 트랜잭션 안에서 통째로 바꾼다.
5. **시간대**: 서버는 UTC라 "자정" 배치가 한국 시간 오전 9시에 돌 수 있다.
   → cron에 `Asia/Seoul`을 지정하고, 날짜는 모두 KST 기준으로 다룬다.
6. **탄소 환산 계수에 근거가 없다.** 음식물 쓰레기 1kg당 CO₂e를 얼마로 칠지, 출처와 함께 decisions에 남긴다.
7. **남의 매장 데이터**: 모든 조회를 세션의 매장 ID로 거르고, 남의 `menu_id`로 입력하면 거부되는지 테스트한다. (6번 딥 태스크 RLS와 이어진다)
8. **폐기가 무엇을 버렸는지 모른다.** `daily_waste`는 하루 총량(kg) 하나뿐이라 폐기분을 재고에서 뺄 수 없고, 재료별 탄소 계수 · 폐기 비용도 못 낸다. (집 PC, 2026-11-07) → 9절
9. **수량이 `REAL`(부동소수)이다.** 0.1 + 0.2 ≠ 0.3이 재고 합계에 쌓인다. → DB는 `NUMERIC`, Java는 `BigDecimal`. (집 PC, 2026-11-07)
10. **유통기한이 식자재마다 하나다.** 우유를 화요일 · 금요일에 들여오면 유통기한이 둘인데 한 칸에 못 담는다 → 9절 로트

## 9. 재고 · 폐기 확장 (논의 중)

> 집 PC에서 시작(2026-11-07). 취업 일정에 쫓기지 않는 자기계발 프로젝트라, 5절 2번(재고 흐름)을 "실제 매장에서 쓸 만한 재고 관리"까지 넓혀 본다.
> 아직 고른 것은 없다. 아래는 후보와 각각 무엇을 배우게 되는지다.

**뼈대 생각: 재고를 숫자 한 칸이 아니라 "원장"으로 둔다.**
`ingredients.current_stock`을 고쳐 쓰는 대신, 재고가 움직일 때마다 한 줄씩 쌓는다(통장 거래 내역처럼). 지금 재고 = 그 줄들의 합.
움직임 종류: 입고 · 판매 차감(BOM) · 폐기 · 실사 조정 · (생산 투입).
→ 5절 2번 A(자동 차감)와 B(실사)를 같이 할 수 있다: 평소엔 자동으로 빼고, 가끔 실사로 맞추면 그 차이가 "조정" 줄로 남는다.

| # | 확장 후보 | 무엇이 생기나 | 배우는 것 |
|---|---|---|---|
| E1 | **재고 원장** (위) | 언제 왜 재고가 바뀌었는지 전부 추적 | 불변 기록 설계, 집계 쿼리, 합계 스냅샷(성능), 트랜잭션 |
| E2 | **로트 · 유통기한** | 입고마다 로트(유통기한 포함). 차감은 유통기한 빠른 것부터(FEFO) | 할당 알고리즘, 동시 차감 시 락(낙관적 · 비관적) |
| E3 | **폐기 원인 · 식자재별 폐기** | 유통기한 만료 / 조리 실수 / 당일 판매 잔여(베이커리) / 손님 잔반. 재료별 탄소 · 원화 손실 | enum · 도메인 모델링, 원인별 분석 쿼리. "판매 잔여"는 과잉 생산 신호라 예측 개선에 쓴다 |
| E4 | **반제품 BOM (중첩 레시피)** | 크루아상 → 반죽 → 밀가루 · 버터. 반죽을 미리 만들어 둘 수 있다 | 재귀 CTE(`WITH RECURSIVE`), 순환 참조 막기 |
| E5 | **구매 단위 ↔ 사용 단위** | 우유는 1L 팩 12개 박스로 사고 ml로 쓴다. 발주는 박스 단위로 올림, 최소 주문량 | 값 객체(Value Object), `BigDecimal`, 단위 변환 |
| E6 | **공급처 · 발주서 → 입고 검수** | 발주(대기 → 보냄 → 일부 입고 → 완료), 리드타임만큼 미리 발주 권장 | 상태 기계, 리드타임을 넣은 발주 계산 |
| E7 | **실사 (재고 조사)** | 이론 재고 vs 실제 → 차이 리포트(로스율) | E1 조정 줄, 리포트 쿼리 |
| E8 | **원가 · 손실 원화** | 입고 단가 → 메뉴 원가율, 폐기 손실을 원으로 | 단가 평균(이동평균 · 선입선출), 사장님에게는 탄소보다 돈이 먼저 와닿는다 |
| E9 | **생산 계획 (베이커리)** | 내일 판매 예측 → 아침에 몇 개 구울지 → 재료 투입 | 예측 → 생산 → 재고가 이어지는 흐름 |

**의존 관계**: E1이 바닥이다. E2 · E3 · E7은 E1 위에 얹힌다. E5는 E6 · E8의 전제. E4 · E9는 서로 붙어 있다.

**우선순위 (안, 2026-11-07 사용자 동의)**: M = E1 원장 + E2 로트 + E3 폐기 원인 · 재료별 / S = E4 반제품 BOM · E5 단위 변환 / L = E6 발주서 · E9 생산 계획. E7 실사 · E8 원가는 아직 안 정함(E7은 E1 위에 얹기 쉬워서 M 끝자락 후보).

### 10.1 v0 개요에서 찾은 구멍

1. 가설("감보다 정확하다")을 확인할 장치가 없다 → **백테스트**: 지난 데이터로 예측을 돌려 실제와 비교. 기준선은 "어제만큼" · "지난주 같은 요일만큼"
2. "전월 대비 폐기 감소"는 판매가 줄어도 줄어든다 → **폐기율**(판매 대비 폐기)로 본다
3. "중소형 F&B"는 너무 넓다 → 대상 업종을 좁힌다 (10.4)
4. 탄소만으로는 매일 입력할 동기가 약하다 → **손실 원화**를 앞에 둔다
5. 매일 입력이 제일 큰 이탈 지점이다 → "어제 값 불러오기" 같은 입력 덜기 장치를 설계에 넣는다
