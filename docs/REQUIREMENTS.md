## 1. 개요

**ZeroWaste F&B** — 베이커리 카페 점주와 직원이 매일 마감 때 판매 · 폐기를 기록하면, 날씨 · 공휴일을 반영해 **내일 무엇을 몇 개 만들고 어떤 재료를 얼마나 발주할지** 알려 주고, 폐기로 잃은 돈 · 폐기율 · 탄소를 보여 주는 웹 앱.

- **대상**: 베이커리 카페 + 델리 메뉴(샐러드 · 샌드위치 · 도시락). 업종을 둘로 받지 않고 **가게 하나 안의 메뉴 분류**로 본다. 앱의 중심 개념은 **"당일 생산 · 당일 폐기 품목"**(빵 · 샐러드 · 도시락)과 **"재료 발주"**(원두 · 우유 · 채소)다 → [decisions/0007](decisions/0007-target-and-metrics.md)
- **문제**: 당일에 만들어 당일에 폐기하는 품목과 유통기한 짧은 재료를 감으로 정해서, 남는 것이 폐기되고 얼마나 낭비됐는지도 모른다.
- **가설**: 판매 기록 + 요일 가중 이동 평균 + 날씨 · 공휴일만으로도 "지난주 같은 요일만큼"보다 예측 오차를 줄일 수 있다 → **백테스트**로 확인한다(F18).
- **성공 지표**: 같은 폐기 데이터를 두 얼굴로 본다.
  - **돈** — 폐기 손실(원) · 폐기율(판매 대비 폐기). 매일 보는 숫자
  - **탄소** — 재료별 CO₂e 감축량. 월간 · 누적으로 보는 숫자. 프로젝트 정체성이라 빼지 않는다
  - 예측 오차는 앱이 제대로 맞히는지 보는 내부 지표
  - 한 줄 메시지: "낭비된 돈을 줄이면 탄소도 같이 줄어든다."
- **계정**: 여러 매장 · 역할(점주 / 직원). 한 사람이 여러 매장에 속할 수 있다.

### 1.1 하지 않을 것

- POS 연동 — 마감 입력은 사람이 한다. 대신 입력 부담을 줄이는 장치를 둔다(F08)
- 딥러닝 예측 — 통계(요일 가중 WMA) + 보정까지
- 예약 · 단체 주문 · 배달(도시락 전문점식 흐름)
- 모바일 앱 — 웹이 휴대폰 화면을 지원한다(N04)

### 1.2 v0 개요에서 고친 것

v0(2026-07, Express) 개요를 다시 보며 찾은 구멍이다. 옛 README는 [archive/README_v0.md](archive/README_v0.md).

1. 가설을 확인할 장치가 없었다 → 백테스트(F18)
2. "전월 대비 폐기 감소"는 판매가 줄어도 줄어든다 → 폐기율
3. "중소형 F&B"는 너무 넓었다 → 베이커리 카페 + 델리
4. 탄소만으로는 매일 입력할 동기가 약하다 → 손실 원화를 앞에
5. 매일 입력이 제일 큰 이탈 지점이다 → "어제 값 불러오기" 등

## 4. 데모 데이터와 한계

**한계**: 실제 매장 데이터가 없다. 그래서 백테스트는 **"날씨가 판매에 영향을 준다"를 증명하지 못한다** — 데모 데이터에 넣은 효과를 예측이 되찾는지, 즉 파이프라인이 제대로 도는지를 확인한다. README와 리포트에 이 한계를 그대로 적는다.

**데모 시드(N03) 규칙** — v0 `seed_dummy.py`의 규칙을 이어받는다(옛 코드는 태그 `v0-express`):
- 매장: 베이커리 카페 + 델리. v0 메뉴 13개(음료 5 · 베이커리 4 · 식사 3 · 신메뉴 말차라떼)에 샐러드 · 도시락과 채소 재료를 더한다
- 기간 약 6개월, 월요일 정기 휴무 + 예외 휴무 몇 날, 요일 가중치 + 노이즈, 고정 시드(재현 가능)
- 콜드스타트: 신메뉴는 마지막 며칠치만 판매 기록
- **새로**: 실제 지역의 과거 날씨(ASOS) · 실제 공휴일을 받아 그 위에 메뉴별 날씨 민감도(아이스 음료 · 샐러드 +, 따뜻한 메뉴 −)를 넣는다. 품절 날 · 남은 수량 · 행방도 만든다
