# 목업

> **화면 시안을 그림으로 비교하고 채택을 표시하는 곳이다** — 시안은 참고 자료다.
> 확정한 규격 · 색 · 문구는 `DESIGN.md`가 원본이고 채택한 뒤에 옮긴다. 화면이 무엇을 받는지는 [REQUIREMENTS](../REQUIREMENTS.md) · [DATA_MODEL 4절](../DATA_MODEL.md#4-마감--재고-규칙).

## 보는 방법

- **화면 하나 = 폴더 하나**(2026-11-09). 폴더 안에 보드 · 휴대폰 · 데스크톱 파일과 그 화면만 쓰는 js · css. 여러 화면이 같이 쓰는 것은 `_shared/`, 화면을 넘나드는 보드(화면 지도 · 이동 틀 · 컬러)는 맨 위
- 파일을 브라우저로 바로 열면 된다(`file://`, 서버 없이). 보드(`closing/Closing.html`)를 열면 시안이 나란히 뜬다 — 휴대폰은 옆으로 스크롤, 데스크톱은 아래로 스크롤. 어디서 시작할지 모르면 `Map.html`
- 화면 파일(`closing/Closing.mobile.html` · `closing/Closing.desktop.html`)을 따로 열면 오른쪽 아래 검은 단추로 시안 · 상태 · 밝기를 바꾼다. 다른 시안 안에 끼울 때는 `embed=1`로 단추를 숨긴다
- `file://`에서는 Chrome이 주소 바꾸기(`history.replaceState`)를 막는다. 보드는 그 오류를 삼키게 해 두었다 — 그래서 보드에서 고른 값이 주소창에는 남지 않는다
- Claude 데스크톱 앱 미리보기에서는 `file://`이 정적 스냅숏으로만 떠서 스크립트가 안 돈다. 그때는 `.claude/launch.json`의 `mockups`(파이썬 `http.server` 5500)로 띄운다. 파이썬이 없는 기기(노트북)는 `mockups-node`(노드 한 줄 서버 5501)
- 주소 파라미터

| 파라미터 | 값 | 기본 |

| `device` | `mobile` · `desktop` (보드만) | `mobile` |

## 파일

```
mockups/
  README.md · Map.html · Shell.mobile.html · Shell.desktop.html · Colors.html   화면을 넘나드는 보드
  _shared/   shared.css · shared.js · forms.css · nav-data.js · stock-data.js    여러 화면이 같이 쓰는 것
  auth/ · store/ · settings/ · members/ · closing/ · loss/                       화면 하나 = 폴더 하나
  receive/ · stock/ · waste/ · count/                                            (재고 묶음)
```

새 화면은 소문자 폴더(`stock/`)를 만들고 그 안에 `화면.html`(보드) · `화면.mobile.html` · `화면.desktop.html`, 그 화면만 쓰는 `화면.js` · `화면.css`. 공용 파일은 `../_shared/`로 읽는다. 다른 화면 폴더의 파일을 읽지 않는다 — 같이 쓰게 되면 `_shared/`로 옮긴다(로고 `ZW.brand`를 그렇게 옮겼다). 이동 틀에 끼울 화면은 `_shared/nav-data.js`의 `src`에 화면 이름(`'Settings'`)을 적으면 `settings/Settings.기기.html`을 찾는다.

## 컬러 — 시안 (E 채택, 2026-11-08)

색 이름은 역할로 둔다: 바탕 · 카드 · 글 · 보조 글 · 주 색(버튼 · 선택) · 손실 · 경고. **손실은 주 색과 따로** 두어 "낭비된 돈"이 화면에서 늘 같은 색으로 보이게 한다. 경고(이미 저장한 날 · 품절)는 모든 시안이 같은 호박색이다. 채택한 값은 [DESIGN 2절](../DESIGN.md#2-색)이 원본이다.

| 시안 | 느낌 | 볼 것 |
|---|---|---|
| A · 숲 | 초록 + 테라코타 손실 | "아낀다 · 친환경"이 바로 읽힌다. 흔한 조합 |
| B · 밀 | 갈색 + 크림, 손실 빨강 | 베이커리답다. 주 색(갈색)과 손실(빨강)이 같은 따뜻한 계열이라 손실이 덜 튄다 |
| C · 청록 | 청록 + 주황 손실 | 주 색과 손실이 보색이라 손실이 가장 또렷하다. 업무 도구 느낌 |
| D · 먹 | 흑백 + 손실 빨강 | 색이 손실 하나뿐이라 시선이 손실로 간다. 차갑고 심심할 수 있다 |
| E · 올리브 | 올리브 초록 + 벽돌 손실 | A보다 흙빛이고 차분하다. 어둡게에서는 연두가 밝게 뜬다 |
| F · 남색 | 남색 + 산호 손실 | 믿음직하고 무겁다. 버튼이 어두워 손실보다 버튼이 먼저 보일 수 있다 |
| G · 파랑 | 선명한 파랑 + 빨강 손실 | 밝고 경쾌한 요즘 앱 느낌. 파랑 · 빨강 대비가 커서 손실이 잘 보인다 |
| H · 자두 | 자두 보라 + 주황 손실 | 디저트 카페 느낌, 흔하지 않다. 손실 주황이 경고 호박색과 가까워 둘이 헷갈릴 수 있다 |

대비율(보드에 표로): 여덟 시안 × 밝게 · 어둡게 모두 본문 4.5 이상을 통과한다. 그리다가 C 밝게의 "손실 글 / 옅은 손실"이 4.4로 모자라 손실 색을 `#c2410c` → `#b53b0b`로 진하게 바꿨다.

## 마감 입력 — 시안 (휴대폰 A + 데스크톱 A 채택, 2026-11-08)

시안끼리 다른 건 **목록을 어떻게 보여 주느냐**뿐이고 동작 규칙은 같다. 채택한 모양과 동작 규칙은 [DESIGN 3절](../DESIGN.md#3-마감-입력)이 원본이다. 아래는 비교 기록이다.

**휴대폰**

| 시안 | 모양 | 볼 것 |
|---|---|---|
| **A · 카드** (채택) | 숫자 하나 받는 메뉴는 한 줄 카드, 당일 생산품은 큰 카드(품절 · 행방을 안에서 펼침) | 스크롤이 길다 |
| B · 표 | 한 줄에 한 메뉴, 숫자 칸만 | 가장 빠르지만 칸이 작아 잘못 누르고, 품절 · 행방이 줄 아래에 빽빽하다 |
| C · 한 품목씩 | 큰 버튼으로 한 메뉴씩 넘기고 마지막에 요약 | 실수는 가장 적지만 매일 13번 넘긴다 |

**데스크톱**

| 시안 | 모양 | 볼 것 |
|---|---|---|
| **A · 표 + 옆 요약** (채택) | 분류마다 표(머리에 n/m · ✓), 오른쪽에 손실 · 폐기율 · 진행 · 아직 안 친 메뉴 · 저장이 따라온다. 줄마다 그 메뉴의 폐기 손실, 분류마다 합계 | 휴대폰 A와 순서가 같아 기기를 바꿔도 낯설지 않다 |
| B · 분류 탭 | 왼쪽 분류 목록(분류마다 n/m · ✓) → 한 분류씩 표 → "다음: 샐러드 →" | 메뉴가 늘어도 한 화면이 짧다. 다른 분류 값을 보려면 넘겨야 한다 |
| C · 한 장 스프레드시트 | 모든 메뉴 · 모든 칸(행방 할인 · 직원식 · 기부, 폐기는 자동)을 한 표에 | 키보드만으로 가장 빠르다. 칸이 13개라 처음엔 낯설고 휴대폰과 모양이 가장 다르다 |

그리다 고친 것(사전 검증에서 발견): 숫자 칸을 바꾸면 화면을 다시 그리는데, 그 사이에 커서가 다음 칸으로 옮겨 가 있어서 다시 그리면 커서가 사라졌다 — 휴대폰 B(표)도 같았다. 다시 그리기를 커서 이동 뒤로 미루고 커서가 있던 칸을 되찾게 고쳤다. 실제 프런트에서도 "입력 중에 표 전체를 다시 그리면 커서를 잃는다"는 같은 함정이 있다.

**고른 이유**: 섞되 겉모양이 아니라 "받는 데이터 모양이 같으면 같은 부품" 규칙으로 섞는다 — 휴대폰 A가 이미 그렇다(한 줄 카드 · 큰 카드). 데스크톱 A는 같은 구조를 넓게 편 것이라 기기를 바꿔도 같은 화면으로 느껴진다. 다른 시안의 좋은 점은 **동작**으로만 가져왔다: 키보드 이동(데스크톱 C), 분류별 n/m(데스크톱 B), 저장 전 빠뜨림 확인(휴대폰 C의 요약 대신). 데스크톱 C는 메뉴(줄)가 늘면 가장 빠르지만 입력 항목(칸)이 늘면 가로로 넘치고 태블릿 폭(768 ~ 1024px)에 안 들어가서, A의 표에 "모든 칸 펼치기" 모드로 나중에 붙인다.

## 오늘 손실 — 시안 (휴대폰 A + 데스크톱 A 채택, 2026-11-08)

F19. 마감을 저장하면 가는 화면이자 매일 여는 첫 화면 후보다. 오늘 값은 마감 입력 시안의 "입력 중"을 저장했다고 보고 맞췄다(메뉴 폐기 ₩18,600 + 재료 폐기 ₩4,200 = ₩22,800).

**휴대폰**

| 시안 | 모양 | 볼 것 |
|---|---|---|
| A · 숫자 먼저 | 오늘 손실 크게 + 지난 일요일 대비 → 메뉴 폐기 · 폐기율 · 절약 → 무엇이 낭비됐나(손실 큰 순 막대) → 절약 → 이번 주 막대 | "얼마 낭비됐지?"에 바로 답한다. 길다 |
| B · 주간 먼저 | 이번 주 합계 + 요일 막대(지난주 점선 겹침), 막대를 누르면 그날 숫자 · 내역 | 흐름이 잘 보이고 지난 날도 본다. 오늘 숫자가 한 단계 아래 |
| C · 문장 | "오늘은 ₩22,800이 낭비됐어요" · "리코타 샐러드가 51%예요" 같은 문장 카드 + 자세히 | 읽기 쉽고 다음 행동을 말한다. 숫자 비교는 느리고 문장을 상황마다 만들어야 한다 |

**데스크톱**: A 대시보드(숫자 넷 · 요일 막대 + 분류별 · 오늘 낭비된 것 표), B 날짜 목록 + 상세(요일 목록 미니 막대 → 그날 숫자 · 표).

**그리면서 정한 것(사전 검증에서 발견)** — 어느 시안을 고르든 같다

| 정한 것 | 이유 |
|---|---|
| 손실 = 메뉴 폐기(레시피로 펼친 원가) **+ 재료 폐기**(로트 단가, F09) | 메뉴만 세면 유통기한 지난 우유 · 손질한 양상추가 빠진다. 표에서 "재료" 표시로 나눈다 |
| 할인 판매 · 직원식 · 기부는 손실이 아니라 **"절약"**으로 따로 | DATA_MODEL 4절 2. 줄인 노력이 보여야 기록할 맛이 난다 |
| 비교는 **지난주 같은 요일**(어제가 아니라) | 베이커리는 요일마다 판매가 크게 다르다 — 예측 기준선(F18)과 같은 눈높이 |
| 손실이 **줄면 주 색(초록), 늘면 손실 색** | 빨강 = 손해. 줄어든 것까지 빨갛게 보이면 헷갈린다 |
| 마감을 안 한 날은 0이 아니라 **점선 막대 + "?"**, 합계 · 지난주 비교에서 **그 요일을 양쪽 다 뺀다** | 0으로 세면 "이번 주 덜 낭비됐다"로 속는다. 이번 주에 값이 있는 요일끼리만 비교 |
| 휴무일은 막대 없이 "휴무", 계산에서 뺀다 | 판매 0과 다르다(F08) |
| 오늘 마감 전이면 숫자 대신 "마감 전" + 마감 입력 버튼, 오늘 막대는 "…" | 0원으로 보이면 오늘 아무것도 낭비되지 않은 줄 안다 |
| 기록이 하나도 없으면 "첫 마감 입력하기" | 처음 쓰는 매장 |
| 폐기율 = 메뉴 폐기 ÷ 만든 수량(당일 생산품). 이번 주는 날마다 폐기율의 평균 | 재료는 "만든 수량"이 없어 폐기율에 넣지 않는다 |

**고른 이유**: 이 화면에 오는 순간은 대부분 마감 저장 직후라 "오늘 얼마 낭비됐지?"가 맨 위여야 한다(A). 마감 입력에서 고른 구조(휴대폰은 카드를 쌓고, 데스크톱은 넓게 편다)와 이어진다. 다른 시안에서는 동작만 가져왔다: B의 **막대를 누르면 그날 보기**(휴대폰은 막대 아래에 그날 카드, 데스크톱은 분류별 · 표가 그날로), C의 **한 줄 요약**("리코타 샐러드가 손실의 51%예요" — 가장 큰 한 가지만). 이번 주는 **월요일 시작 고정**, 금액은 원 단위 전부 · 막대 위만 "2.3만". 규칙은 [DESIGN 7절](../DESIGN.md#7-오늘-손실)이 원본.

## 앱 화면 지도 — 이동 시안 (휴대폰 A + 데스크톱 A 채택, 2026-11-08)

화면을 하나씩 그리다 보니 "화면들이 어떻게 이어지는지"를 정한 적이 없었다. [Map.html](Map.html)에 한 장으로 모았다.

- **흐름**: 소개(F27) → 로그인 · 가입(F01, 직원은 초대 링크) → 첫 매장 등록(F02) 또는 매장 고르기(매장이 둘 이상일 때만) → 앱. 앱 안의 화면은 매일(오늘 · 마감 · 내일 권장) · 재고(재고 · 입고 · 재료 폐기 · 실사) · 리포트 · 설정(메뉴 · 레시피 · 매장 · 직원) 네 묶음
- **하루 흐름**: 아침 오늘 만들 것(M4) → 낮 입고 · 재료 폐기 → 마감 입력 → 마감 후 오늘 손실 → 밤 예측 배치. 그래서 첫 화면은 **시간이 아니라 "마감했나"로 바뀌는 "오늘"** 하나(안) — 마감 전이면 맨 위에 마감 입력 버튼, 후면 오늘 손실. 오늘 손실 시안의 "마감 전" 상태가 이미 그 모양이다. 직원은 "마감"으로 연다
- **이동 시안**: 휴대폰 A 아래 탭(오늘 · 마감 · 재고 · 리포트 · 더보기) · B 가운데 큰 마감 버튼 · C 탭 없이 홈에서 들어가기, 데스크톱 A 왼쪽 메뉴 · B 위쪽 메뉴
- **점주와 직원**: 직원 메뉴는 마감 · 입고 · 재료 폐기 + 매장 바꾸기 · 로그아웃(F03)

**정한 것**: 휴대폰 A 아래 탭 · 데스크톱 A 왼쪽 메뉴 — 데스크톱 메뉴는 **폭을 끌어 조절하고 접을 수 있게**(사용자 요청). 첫 화면은 점주 "오늘"(마감 여부로 스스로 바뀜) · 직원 "마감", 직원에게는 금액을 숨긴다(마감 입력 시안에 `role=staff`로 반영). B(가운데 마감)는 "오늘"이 마감 전에 큰 버튼을 띄워 겹치고, C(홈에서 들어가기)는 화면을 옮길 때마다 홈을 거쳐서 뺐다. 규칙은 [DESIGN 8절](../DESIGN.md#8-앱-이동--첫-화면).

## 로그인 · 가입 · 초대 — 시안 (휴대폰 A + 데스크톱 B 채택, 2026-11-09)

[auth/Auth.html](auth/Auth.html). 휴대폰 A 로그인 / 가입 탭 · B 이메일 먼저, 데스크톱 A 가운데 카드 · B 왼쪽 소개 + 오른쪽 입력.

- **B(이메일 먼저)의 대가**: 이메일만 넣어도 "가입된 사람인지"가 드러난다(계정 존재 노출). A는 로그인 실패 문구를 "이메일이나 비밀번호가 맞지 않아요" 하나로 둬서 어느 쪽이 틀렸는지 말하지 않는다
- **그리면서 정한 안**(채택 뒤 DESIGN으로): 비밀번호 8자 이상 · 조합 규칙 없음, 5번 실패하면 15분 잠김, 가입 칸은 이름 · 이메일 · 비밀번호 셋, "데모 매장 둘러보기"(읽기 전용)
- **초대 링크**는 열어 본 사람의 사정이 넷이라 상태를 나눴다: 계정 없음(가입하며 들어가기) · 로그인됨(수락만, 내 계정이 아니면 로그아웃) · 이미 구성원(링크를 쓰지 않음) · 쓸 수 없음(만료 · 이미 쓰임 · 취소를 한 문구로). 초대 화면에는 누가 · 어느 매장 · 역할 · 기한과 "직원이 하는 일 · 금액은 점주만"을 먼저 보인다
- 가입한 뒤: 점주는 첫 매장 등록, 초대로 들어온 직원은 매장 등록 없이 마감
- **아직 안 정한 것**: 비밀번호 찾기 — M2에는 메일 발송이 없다. 처음 안 "점주가 직원 비밀번호를 다시 정해 줌"은 다른 매장 계정까지 넘어가서 버렸다(DESIGN 9.4)

**정한 것**: 휴대폰 A 탭 · 데스크톱 B 소개 + 입력 — 휴대폰 B는 계정 존재가 드러나고 한 번 더 누른다. 문구는 사용자가 다듬었다: 보안 안내(실패 · 잠김)는 합쇼체, 점주를 부를 때는 "사장님", 만료 · 사용 · 취소는 "만료되었어요" 한 문구. 규칙은 [DESIGN 9절](../DESIGN.md#9-로그인--가입--초대).

## 첫 매장 등록 · 매장 고르기 — 시안 (C 채택, 2026-11-09)

[store/Store.html](store/Store.html). 휴대폰 A 한 화면(이름 → 주소 검색 → 등록) · B 3단계(이름 · 주소 · 확인) · C 한 화면 + 질문형(A의 흐름에 B의 큰 질문 제목 · 처음 시작 진행 막대, 이름 전에는 주소 칸이 흐림 — "B가 요즘 느낌, A가 편함"이라 둘을 섞어 봤다). 데스크톱은 로그인(데스크톱 B)과 같은 틀에 왼쪽을 "처음 시작" 단계(가입 · 매장 등록 · 메뉴 준비 · 첫 마감)로 바꿨다.

- **받는 것은 이름과 주소뿐**(상세 주소는 선택). 격자 · 관측 지점 · 지역 코드는 서버가 주소로 계산하고, 화면에는 "이 위치로 날씨 · 공휴일을 가져와요 · 가까운 관측소"만 보인다
- **주소 검색이 실패해도 등록은 막지 않는다** — 외부 데이터는 보조 신호다(REQUIREMENTS 3절). "주소 없이 먼저 등록"하면 날씨 신호만 빠지고 매장 설정에서 나중에 넣는다. 0건이면 입력 예시(도로명 + 건물번호 · 건물 이름)를 보인다
- **매장 고르기**: 매장이 둘 이상일 때만. 마지막에 연 매장이 맨 위, 줄마다 역할(점주 · 직원)과 오늘 마감 여부. 직원으로 연 매장은 마감으로, 점주는 오늘로
- **매장 없음**(사정 하나 더 찾음 — 직원에서 빠진 사람은 로그인해도 갈 매장이 없다): 초대 링크를 받으라는 안내 + "내 매장 등록하기"
- **시작 체크리스트**: 등록 직후 · 메뉴가 0개인 매장의 "오늘". 매장 등록 ✓ → 메뉴 → 식자재(기본 단가) → 레시피 → 첫 마감, 다음 할 일에만 단추. "레시피 없이도 마감은 되지만 손실 금액은 레시피와 단가가 있어야 나와요"를 밝힌다. 데스크톱 시안에서는 등록 틀 안에 그렸지만 실제로는 앱 틀(왼쪽 메뉴) 안의 "오늘" 자리다

**정한 것**: C 한 화면 + 질문형 — 사용자가 "B가 요즘 느낌, A가 편함"이라 고르지 못해 둘을 섞은 C를 그렸고 채택했다. B의 화면 나누기는 칸이 둘뿐이라 누르는 횟수만 늘어서 뺐다. 규칙은 [DESIGN 10절](../DESIGN.md#10-첫-매장-등록--매장-고르기).

## 메뉴 · 식자재 · 레시피 — 시안 (휴대폰 A + 데스크톱 A 채택, 2026-11-09)

[settings/Settings.html](settings/Settings.html). 점주만 보는 설정. 한 화면 안에 메뉴 / 식자재 탭, 레시피는 메뉴 상세 안에. 휴대폰 A 상세 화면으로 넘어감 · B 아래 시트, 데스크톱 A 목록 + 상세 · B 표에서 바로 고치기(▸로 펼치면 레시피).

- **메뉴**: 이름 · 분류(고정 5) · 만드는 방식(미리 만들어 둠 = 당일 생산품 / 주문 때 만듦) · 판매가 · 레시피. 레시피에서 **1개 원가 · 원가율**이 바로 나온다. 판매가를 바꾸면 오늘 마감부터 적용, 지난 기록은 그날 값
- **식자재**: 이름 · 기본 단위(g · ml · 개) · 기본 단가 · 탄소 분류 · 사용 중인 메뉴. 단가는 **사는 단위 그대로**(20,000원 / 20kg) 넣고 "= 1g당 1원"을 보여 준다 — 1g당 값을 사람이 계산하게 하지 않는다
- **빈 값은 0이 아니라 표시한다**: 레시피 없는 메뉴는 "레시피 없음", 단가 없는 재료는 "단가 없음"과 원가 뒤 "+ ?"(원가율 —), 탄소 분류 없는 재료는 "탄소에서 제외돼요". 목록 위에 "채울 것 n개"
- **레시피에서 재료를 찾다 없으면 그 자리에서 새 식자재**(이름 · 단위 · 단가는 나중에 넣어도 됨) — 시작 체크리스트의 메뉴 → 식자재 → 레시피를 오가지 않게
- **잠금 · 중지**: 레시피에 쓰인 식자재는 단위를 못 바꾼다(자물쇠 + 이유). 메뉴는 판매 중지, 식자재는 사용 중지 — 지우지 않고 목록 아래로 접는다
- **그리면서 찾은 것**(사전 검증): 1단위당 단가가 원 미만이라 "돈은 bigint"와 부딪친다 → 가격 / 양 두 값으로 저장. `개` 단위 재료는 탄소 계산에 1개 무게가 필요하다 → [DATA_MODEL 5절](../DATA_MODEL.md#5-기술-규칙). 버터처럼 탄소 분류(OWID 약 40종)에 딱 맞는 게 없는 재료가 있다 → 가장 가까운 것을 고르게 안내

**정한 것**: 휴대폰 A 상세 화면 · 데스크톱 A 목록 + 상세 — 레시피가 길어 아래 시트(B)는 키보드와 함께 좁고, 표(B)는 처음 많이 넣을 때만 빨라 나중 "한 번에 넣기" 모드 후보로 남겼다. 문구는 사용자가 다듬었다(쓰다 → 사용하다 · 측정해요 · 판매하는 · 알맞은 · 제외된 · 분류돼요, DESIGN 6절). 화면 지도 · 이동 틀(Shell)에서 "메뉴 · 레시피"가 이 시안을 끼워 보인다. 규칙은 [DESIGN 11절](../DESIGN.md#11-메뉴--식자재--레시피).

## 매장 · 직원 — 시안 (휴대폰 A + 데스크톱 B 채택, 2026-11-09)

[members/Members.html](members/Members.html). 점주만 본다. 휴대폰 A 한 화면(매장 카드 → 사람 카드, 초대는 카드 안에서 펼침) · B 탭 + 아래 시트, 데스크톱 A 한 줄(폭 720) · B 두 칸 + 사람 표. 내보내기 확인은 모두 따로 묻는다(휴대폰 시트 · 데스크톱 창).

- **매장**: 이름 · 주소. 주소를 바꾸면 **오늘부터** 새 위치의 날씨, 지난 기록은 그대로. 주소 없이 등록한 매장은 "주소 넣기"
- **초대 링크**: 한 사람 한 링크 · 7일 · 한 번 사용하면 끝. 복사 · 공유(휴대폰 공유 창). 대기 중인 초대는 목록에 남고 취소할 수 있다 — 로그인 시안의 "만료되었어요"(만료 · 사용 · 취소)와 짝
- **내보내기**: 바로 막힌다(decisions/0006 "내보내면 바로 막혀야"), 계정과 다른 매장 일은 그대로, 그 직원이 입력한 지난 기록 · 이름은 남는다, 다시 하려면 새 초대
- 점주 줄에는 내보내기가 없다. 점주는 한 명(넘기기 · 공동 점주는 아직 범위 밖)
- **그리면서 찾은 것**(사전 검증): 로그인 시안의 "사장님이 직원 비밀번호를 다시 정해 줌"은 위험하다 — 계정 하나가 여러 매장에 속하고 다른 매장의 점주일 수 있어서, 한 매장 점주가 그 계정을 통째로 가져간다. 그래서 버렸다 → [DESIGN 9.4](../DESIGN.md#94-아직-안-정한-것)

**정한 것**: 휴대폰 A 한 화면 · 데스크톱 B 두 칸 + 사람 표 — 휴대폰은 내용이 짧아 탭으로 나눌 이유가 없고, 데스크톱은 직원이 늘면 표가 읽기 쉽다. 화면 지도 · 이동 틀(Shell)의 "매장 · 직원"이 이 시안을 끼워 보인다. 규칙은 [DESIGN 12절](../DESIGN.md#12-매장--직원).

## 입고 — 시안 (휴대폰 A + 데스크톱 A 채택, 2026-11-09)

[receive/Receive.html](receive/Receive.html). M3 첫 화면 — 재고 묶음 넷(입고 → 재고 → 재료 폐기 → 실사) 중 로트를 만드는 화면이라 먼저 그렸다. 점주는 재고 탭 위쪽 칩, 직원은 아래 탭 "입고"로 들어온다(DESIGN 8.2). 휴대폰 A 한 줄씩 더하기(찾기 → 카드, 고치는 줄 하나만 펼침) · B 목록에서 고르기(자주 들어오는 재료부터 체크), 데스크톱 A 표 + 옆 요약(마감 입력 데스크톱 A 틀) · B 왼쪽 기록 + 오른쪽 카드(메뉴 · 레시피 데스크톱 A 틀).

- **입고 한 번 = 명세서 한 장**, 줄 하나 = 로트 하나(재료 · 양 · 유통기한 · 금액). 같은 재료라도 유통기한이 다르면 줄을 나눈다
- **양**은 큰 단위로 넣고 기본 단위로 저장(2kg → 2,000g, 12L → 12,000ml). 박스 단위(F07)는 S라 이번 범위 밖
- **유통기한** 칩: "지난번처럼 n일"(재료마다 지난 입고의 기한 간격) · +3일 · +7일 · 없음. 이미 지난 날이면 막지 않고 묻는다(받자마자 폐기할 것이면 재료 폐기로). 없음(소금 · 설탕)은 차감 때 맨 뒤 · 임박 경고 제외. 임박은 오늘 · 내일, 지남은 만료 — 고정
- **금액은 줄 전부, 명세서 금액 그대로**(식자재 기본 단가와 같은 "사는 단위 그대로"). 옆에 1kg · 1L · 1개당 값과 기본 단가 비교(5% 넘게 다르면 ▲ 비싸요 · ▼ 싸요 — 나중 F22 가격 변동 알림의 씨앗). 비워 두면 기본 단가로 계산, 기본 단가도 없는 재료는 "손실에서 제외"를 밝히고 "이 값을 기본 단가로도 저장"을 권한다
- **직원 화면에는 금액이 없다**(2026-11-09 사용자 결정 — 단가는 점주가 나중에). 직원이 넣은 줄은 단가가 빈 채로 저장되고, 점주 화면의 입고 기록 탭에 "단가 n", 줄마다 "단가 확인 n줄"
- **식자재는 점주만 만든다**: 찾다 없으면 점주는 그 자리에서 새 식자재(이름 · 단위, 탄소 분류 · 기본 단가는 나중에), 직원은 "사장님께 알려 주세요"
- **그리면서 찾은 것**(사전 검증): 단가를 나중에 넣으면 그 로트를 **이미 차감한 날의 손실이 기본 단가로 계산돼 있다**. "그날 원가를 찍어 둔다"(DATA_MODEL 5절)를 그대로 따르면 점주가 단가를 넣어도 지난 손실이 안 고쳐진다 → 단가 채우기 화면에 "11월 7일 마감에서 사용함 — 그날 손실을 입고 단가로 다시 계산해요"를 띄우는 안. 판매가 변경(지난 기록은 그날 값)과 다르게 **"몰랐던 값을 채움"은 다시 계산**으로 본다 — 채택 때 DATA_MODEL에 규칙으로
- 입고를 고쳐 양을 줄이면 원장에 고침 줄이 더해지고, 이미 사용한 양보다 적게는 못 고친다(DATA_MODEL 4절 6 원장은 추가만)
- 이동 틀(Shell)의 재고 칩 · 직원 아래 탭 "입고"가 시안 A를 끼워 보인다. 칩 아래에 끼운 화면은 칩 높이만큼 줄여 아래 고정 바가 탭에 가리지 않게 고쳤다

**정한 것**: 휴대폰 A 한 줄씩 더하기 · 데스크톱 A 표 + 옆 요약 — 마감 입력(휴대폰 카드 · 데스크톱 표 + 옆 요약)과 손놀림이 같아 새로 배울 게 없다. B(목록에서 고르기)의 장점은 A 안의 "자주 들어오는 재료" 칩으로 가져왔고, 데스크톱 B(기록 + 입력)는 기록이 길어지면 입력 칸이 좁아진다. 단가를 나중에 채우면 지난 손실을 다시 계산하는 규칙은 [DATA_MODEL 4절 10](../DATA_MODEL.md#4-마감--재고-규칙). 규칙은 [DESIGN 13절](../DESIGN.md#13-입고).

## 재고 — 시안 (휴대폰 A + 데스크톱 A 채택, 2026-11-09)

[stock/Stock.html](stock/Stock.html). 점주만(직원 메뉴에 없음, DESIGN 8.4). 휴대폰 A 재료 목록(위에 "확인할 것" 카드) · B 유통기한 순(로트를 지남 · 오늘 · 내일 · 이번 주 · 그 뒤로 묶음), 데스크톱 A 재료 표 + 오른쪽 상세 · B 위 숫자 넷 + 로트 표. 재료를 누르면 상세(지금 재고 · 며칠치 · 재고 금액 → 로트(차감 순서) → 원장)는 넷 다 같다.

- **재고 = 로트 남은 양의 합**, 재료마다 **며칠치**(만료 안 된 재고 ÷ 최근 7 영업일 하루 평균 사용량) — 발주 권장(F17, M4) 전까지 "언제 사야 하지?"에 답하는 자리
- **확인할 것**: 만료(재료 폐기로) · 오늘 · 내일까지 · 부족(맞추기) · 단가 확인(입고 기록으로). 입고 화면의 "단가 n"과 같은 수
- **로트**는 차감 순서대로 번호(1이 다음 마감에서 먼저), 남은 양 / 처음 양 막대, 입고일 · 1단위당 단가 또는 "단가 비어 있음 — 기본 단가로". **원장**은 날짜 · 무엇(입고 · 마감 사용 · 재료 폐기 · 실사 조정 · 입고 고침 · 부족) · 양 · 그 뒤 남은 양
- **재고 금액** = 만료 안 된 로트의 남은 양 × 입고 단가(없으면 기본 단가, 둘 다 없으면 "+ ?"). 만료 로트 금액은 "만료 ₩n 따로"
- **그리면서 찾은 것**(사전 검증)
  - **아침에 재고를 보면 오늘 사용량이 아직 안 빠져 있다** — 재료는 마감 입력 때 한 번에 뺀다(DATA_MODEL 4절 3). "왜 안 줄었지?"가 생겨서 맨 위에 "11월 7일 마감까지 사용량을 뺐어요 · 오늘 입고는 더했어요 · 오늘 마감하면 다시 계산돼요"를 늘 띄운다
  - **만료 로트를 차감 순서(FEFO) 맨 앞에 두면 폐기가 숨는다** — 유통기한 지난 토마토를 실제로는 폐기했는데 기록을 안 하면, 다음 마감이 그 로트에서 먼저 빼서 "사용함"이 되고 손실에 안 잡힌다. 그래서 **만료 로트는 차감하지 않고 따로 둔다** → "재료 폐기로 기록"(원인 · 로트 · 양이 채워진 채로) 또는 "아직 사용할 수 있어요"(유통기한 고침, 원장에 남음). 만료 안 된 로트가 모자라도 만료 로트에서 빼지 않고 부족으로 남긴다(DATA_MODEL 4절 5)
  - **부족**: 마감에서 필요한 양이 재고보다 많으면 0에서 멈추고 모자란 양을 원장에 "부족" 줄로(M3 첫 사전 검증 안). 상세에 이유 세 가지(입고 빠뜨림 · 레시피 양 · 입고 양 오타)와 "빠뜨린 입고 넣기 · 실사로 맞추기 · 레시피 보기"
  - **재고를 한 번도 넣지 않은 재료는 부족으로 올리지 않는다** — M2부터 쓰던 매장은 처음엔 로트가 0이라 마감마다 모든 재료가 "부족"이 된다. 로트가 한 번이라도 생긴 재료부터 센다
  - **처음 재고는 실사로**: 입고는 "오늘 들어온 것"이라 이미 있던 재료를 넣으면 입고 기록 · 단가 비교가 섞인다. 빈 화면의 주 버튼이 "처음 재고 넣기 (실사)", 처음 넣은 양은 기본 단가로 로트가 된다

**정한 것**: 휴대폰 A 재료 목록 · 데스크톱 A 재료 표 + 상세 — 재고 화면에 오는 질문은 대부분 "이 재료 얼마나 남았지?"라 재료 단위가 먼저다. "무엇부터 쓰지?"는 확인할 것 카드가 맡는다. B(유통기한 순)는 같은 재료가 여러 묶음에 흩어져 합계를 머리로 더해야 한다. 차감 · 부족 규칙은 [DATA_MODEL 4절](../DATA_MODEL.md#4-마감--재고-규칙) 5 · 11, 화면 규칙은 [DESIGN 14절](../DESIGN.md#14-재고).

## 재료 폐기 — 시안 (휴대폰 A + 데스크톱 A 채택, 2026-11-09)

[waste/Waste.html](waste/Waste.html). 점주는 재고 탭 칩, 직원은 아래 탭 "재료 폐기"(DESIGN 8.2). 휴대폰 A 한 건씩(폼 하나 → 저장, 아래 오늘 기록) · B 여러 줄 한 번에(입고처럼 줄을 쌓고 "만료 로트 불러오기"), 데스크톱 A 한 건 폼 + 오늘 기록 · 이번 주 원인별 · B 여러 줄 표 + 옆 요약. 오늘 재료 폐기 합계는 오늘 손실 시안의 "재료 폐기 ₩4,200"(쌀 800 + 양상추 1,600 + 방울토마토 1,800)과 맞췄다.

- 받는 것: **재료 · 원인(유통기한 만료 · 조리 실수 · 손질 · 기타 — 기타면 메모 필수) · 양 · 로트**. 원인과 양이 없으면 저장 잠금
- **로트는 자동, 바꿀 수 있음**: 원인이 유통기한 만료면 만료 · 임박 로트가 위, 그 밖은 유통기한 빠른 로트부터(마감 차감과 같은 순서). 한 로트로 모자라면 다음 로트에서 이어서 뺀다(양상추 600g = 11/4 로트 400g + 11/7 로트 200g)
- **손실 미리 보기**(점주): 양 × 로트 단가(없으면 기본 단가), 두 로트면 둘 다 보인다. 저장하면 오늘 손실의 "재료"로 더해진다. 직원 화면에는 금액이 없다
- **재고 화면 "재료 폐기로"에서 오면** 원인 · 로트 · 양(로트 전부)이 채워져 있다. 만료 로트를 폐기로 기록하면 재고의 "따로 둠"이 없어진다
- 고칠 때는 지우지 않는다 — 원장에 고침 줄(DATA_MODEL 4절 6)
- **그리면서 찾은 것**(사전 검증)
  - **탄 크루아상 한 판은 재료 폐기인가 메뉴 폐기인가?** 마감은 "만든 수량 × 레시피"로 재료를 빼는데, 탄 판은 진열을 안 해서 만든 수량에 안 들어간다 → 재료가 안 빠지고 손실에도 안 잡힌다. 그래서 **"만든 메뉴" 폐기**를 두고 레시피로 재료를 펼쳐 뺀다(DATA_MODEL 1절 `waste_record`의 대상 "재료 또는 메뉴"). 대신 **두 번 세지 않게** "마감의 만든 수량에 넣지 않은 것만 — 팔려고 내놨다 남은 건 마감에서"를 화면에 밝힌다
  - 만든 메뉴를 펼친 재료 중 재고가 모자란 것(버터)은 마감과 같이 0에서 멈추고 부족으로(DATA_MODEL 4절 11)
  - 재고를 한 번도 넣지 않은 재료의 폐기: 재고는 그대로, 손실만 기본 단가로 기록
  - 이번 주 원인별 합계(데스크톱 A, 점주): "무엇을 고치면 줄어드나"로 이어진다 — 만료가 크면 덜 사기(재고의 며칠치), 손질이 크면 F23 가식부 비율(L)

**정한 것**: 휴대폰 A 한 건씩 · 데스크톱 A 한 건 폼 + 기록 — 폐기는 대부분 일하다 한 건씩 생기고, 재고 화면에서 넘어오면 저장 한 번이다. 사용자가 데스크톱 B(여러 줄 표)를 고민했는데, 몰아서 하는 폐기(냉장고 정리)는 거의 만료 · 임박 로트라 앱이 이미 안다 → **재고 화면 "만료 · 임박 로트 한 번에 폐기"**(체크 목록, [stock/Stock.mobile.html](stock/Stock.mobile.html)`?state=bulk`)로 B의 장점만 가져왔다. 기기마다 입력 방식이 갈리지 않는다. 규칙은 [DESIGN 15절](../DESIGN.md#15-재료-폐기).

## 실사 — 시안 (휴대폰 A + 데스크톱 A 채택, 2026-11-09)

[count/Count.html](count/Count.html). 점주만, 재고 탭 칩 "실사". 휴대폰 A 먼저 셀 것부터(부족 · 만료가 있는 재료 → 나머지 식자재 순) · B 보관 위치별(냉장고 · 냉동고 · 상온 선반 — 식자재에 "보관 위치" 칸을 더하는 안), 데스크톱은 같은 순서를 표 + 옆 요약(기준 · 합계 · 저장)으로.

- 줄마다 **장부(지금 재고) · 센 양 · 차이 · 차이 금액**. 아직 안 센 줄은 점선 + "장부와 같아요"(한 번에 채움) — 대부분 재료는 장부와 같아서
- **센 것만 맞춘다** — 안 센 재료는 그대로. 다 세야 저장되면 실사를 미룬다
- 모자란 양은 유통기한 빠른 로트부터, 남는 양은 가장 최근 로트에(DATA_MODEL 4절 7). **부족이 있던 재료를 세면 부족이 정리된다**(버터: 장부 0 · 부족 350g → 센 650g)
- **만료 로트는 세지 않는다** — "만료 로트 300g 따로 — 아직 있으면 세지 말고 폐기로 기록". 섞어서 세면 만료분이 다시 쓸 수 있는 재고로 돌아온다
- **장부와 절반 넘게 다르면** 빨간 테두리 + "0을 하나 더 쳤나요?" — 막지는 않는다(밀가루 13.9kg을 139로 친 예)
- **그리면서 찾은 것**(사전 검증)
  - **언제 센 양인가가 중요하다** — 재고는 마감 때 한 번에 빠지므로, 영업 중(오후 3시)에 세면 아침 사용분이 빠진 양을 세게 되고, 밤 마감이 그 양을 또 뺀다 → 재고가 실제보다 적어진다. 그래서 실사에 **기준**을 붙인다: "어제 마감 뒤 · 영업 전" 또는 "오늘 마감 뒤". 오늘 마감 전에 열면(영업 중) 기준을 고르기 전엔 저장 잠금 + 이유 설명. 기준보다 앞선 날의 마감을 다시 저장하면 "실사 뒤라 재고가 다시 어긋나요"를 띄운다(DATA_MODEL 4절 12)
  - **실사 차이는 오늘 손실에 넣지 않는다** — 언제 생긴 차이인지 모른다(시식 · 깨진 달걀 · 레시피 오차가 며칠에 걸쳐 쌓임). 원장에 "실사 조정"으로 남고 차이 추이는 F12a(S) 리포트에서
  - **처음 재고 넣기** = 실사의 한 상태(재고 화면 빈 화면에서 옴): 장부 · 차이 칸이 없고, 센 양이 기본 단가로 첫 로트가 된다(유통기한은 넣거나 비움). 다 세지 않아도 된다 — 안 센 재료는 "로트가 한 번도 없는 재료"로 남아 마감에서 빼지도 부족으로 올리지도 않는다(DATA_MODEL 4절 11)

**정한 것**: 휴대폰 A 먼저 셀 것부터 · 데스크톱 A 표 + 옆 요약 — 지금 데이터만으로 되고 식자재가 15개 남짓이라 위치로 묶지 않아도 금방 센다. B(보관 위치별)는 세는 동작에 더 맞지만 식자재 칸이 하나 는다 — 재료가 많아지면 다시 본다. 사용자가 처음에 B + B를 골랐다가 A + A로 바꿨다. 규칙은 [DESIGN 16절](../DESIGN.md#16-실사).
